
# Complete backup and restore

**Status** — Finalized draft awaiting explicit specification approval. The three refinement decisions were approved and are recorded in the [decision log](complete-backup-restore-decisions.md).

An ordinary deck export carries spell references. After browser data is cleared, that file alone cannot recover its custom spells. Existing exports also leave users to export each saved deck separately and cannot reconstruct the working deck's saved association and baseline. One complete YASCG backup must let a user recover the collection after clearing browser data or move it to another compatible browser installation.

## Verified current behavior

- Dexie stores `activeDeck`, `savedDecks`, `customSpells`, and `srdSpellOverrides` in the same IndexedDB database. Its existing upgrades cover duplicate deck entries, saved revisions and recoverable legacy baselines, and the introduction of the automatic fit mode. A migrated active deck can have an associated snapshot and a baseline without a saved revision token. [Database schema and migrations](../../../src/db/database.ts) · [Migration tests](../../../src/db/db.test.ts)
- The active record stores committed name and entries, optional saved-deck association, and a baseline used to calculate dirty state and guard a later Save. Snapshots have their own IDs, revisions and modification times. Their list is sorted by most recently updated. Each entry stores its ID, source and spell ID, fallback name, and fit mode. [Deck models](../../../src/domain/deck.ts) · [Saved-deck reads and writes](../../../src/db/saved-decks.ts)
- Deck-only JSON carries the deck name and ordered references. Its importer creates fresh entry IDs, deduplicates references, and clears the active association and baseline. Custom-spell JSON carries definitions and locale-specific SRD override text, omits override timestamps, and supports collision choices. Its importer may assign new IDs to custom spells. These formats serve different purposes from a faithful collection restore. [Export](../../../src/io/export.ts) · [Deck import](../../../src/io/import-deck.ts) · [Custom import](../../../src/io/import-custom.ts) · [Existing formats and behavior](../MAIN-spec.md#8-json-import-and-export)
- Saved decks can retain a reference to a deleted custom spell. The resolver matches by ID and source, preserves missing-reference placeholders, and treats a known SRD spell missing from the selected translation separately. Restoring the stored reference and fallback name is necessary to preserve those cases. Overrides are keyed by SRD ID and locale. The current override editor and importer validate against canonical SRD spell data and supported locales. [Custom spell deletion](../../../src/db/custom-spells.ts) · [Reference resolution](../../../src/services/data/resolution.ts) · [Override validation](../../../src/domain/srd-overrides.ts)
- The selected language preference lives in `localStorage`, outside the transaction spanning the four collection stores. Card design, background selection, and print options are session state. Cached assets, including background images, are bundled. [Language persistence](../../../src/services/data/language.ts) · [App state](../../../src/state/AppProvider.tsx) · [Print options](../../../src/components/print/PrintDialog.tsx) · [Privacy and storage audit](../../privacy-and-legal.md#storage-inventory)
- Existing writes use transactional revision checks for active and saved decks and reviewed fingerprints for custom-spell imports. Broadcast notifications are advisory. A restore can replace records with values whose revision tokens coincide with those held by an open tab. Transactional replacement alone does not invalidate stale work. [Active writes](../../../src/db/active-deck.ts) · [Saved writes](../../../src/db/saved-decks.ts) · [Custom import](../../../src/io/import-custom.ts) · [Notifications](../../../src/db/notifications.ts) · [Cross-tab browser coverage](../../../e2e/srd-overrides-sync.spec.ts)

The current regression baseline includes transactional rollback, stale deck revisions, legacy migrations, deck import normalization, custom-spell collisions, validation of SRD overrides, cross-tab refresh, and offline startup. ## Requirements

### CB-1 — Collection contents and fidelity

| Backup section | Required contents |
| --- | --- |
| Active deck | The last committed working deck, including changes not saved to a named snapshot. Preserve its name, ordered entries, association to a saved deck, baseline name and ordered entries, saved revision token when present, and active revision. If the singleton has never been initialized, represent the default empty active deck. |
| Saved decks | Every snapshot, including empty snapshots and snapshots that share a name. Preserve IDs, names, timestamps, revisions, and ordered entries. The existing most-recently-updated list behavior and tie order must survive the round trip. |
| Custom spells | Every supported persisted field and value of every custom definition, including unused spells, editable copies, original IDs, optional fields and timestamps, ordered arrays, and stored text and Markdown. Preserve field presence and text content as stored. |
| SRD overrides | Every persisted override for every supported locale, regardless of selection. Preserve its spell ID, locale, verbal and somatic note fields as stored, and timestamp. An override applies only to its matching locale through existing resolution behavior. |

Preserve each entry's ID, spell ID, reference source, fallback name, and fit mode in the active deck, saved snapshots, and baseline. Keep unresolved custom and SRD references as recorded. When the receiving catalog lacks a bundled spell or translation, use existing missing-reference or translation-unavailable behavior. Never match by name, substitute spells, or generate replacement IDs.

Preserve the association, baseline, dirty status, and existing conflict or recovery behavior. For example, a migrated association can lack a verifiable saved revision. Preserve that state so existing Open or Save As recovery still applies. A stale baseline is also valid and must not be silently rebased to the current snapshot.

The destination browser's language preference remains unchanged. Session-only drafts, selections, filters, undo history, card design, background selection, and print controls are outside the backup. Bundled spell definitions, translations, backgrounds and other cached assets remain supplied by the installed app. Internal concurrency metadata belongs to the destination and is excluded from the portable collection.

### CB-2 — Complete backup export

Provide a clearly named, collection-level export action. One activation initiates a single JSON download without requiring the user to save the active deck as a snapshot, choose records, or export individual files. Export one consistent snapshot of committed collection data across all four stores, including when another tab writes concurrently. Export must not commit pending editor input or change the collection.

Export an empty collection on request. If reading or serializing the collection fails, report the failure and produce no partial backup. A complete backup generated by a compatible build must be accepted by that build's file validation for supported data. Do not reuse the narrower import flows' size or entry limits if they would reject a collection that the running app can export. If a technical resource limit prevents handling a file, report it explicitly without producing a truncated backup or changing the collection.

### CB-3 — Versioning, validation, and compatibility

Use a dedicated JSON object with a distinct backup type discriminator, an explicit integer format version starting at 1, and all four collection sections. Require all sections, even when their collections are empty. Keep the format version independent of the application, bundled catalog, and IndexedDB schema versions. The coverage and record semantics in CB-1 define the v1 data contract. Existing deck-only and custom-spell JSON remain separate and are rejected by complete restore. The existing import flows reject complete backups as the wrong type.

Validate and, when supported, migrate entirely before allowing a destructive confirmation. Check the envelope, version, record fields, uniqueness of store keys and of entry and spell identities within each deck entry list, and supported deck association and baseline states. Validate the stored source and ID fields without requiring a deck spell to exist in the source it names. An entry whose ID exists only under another source still has a valid unresolved reference. Support legacy states produced by existing IndexedDB upgrades, including an associated deck with a stored baseline and no saved revision because the snapshot was missing or could not be verified. Reject ambiguous or unsupported data that would require dropping fields or records, deduplicating, trimming persisted values, repairing relationships, or supplying guessed values. Domain validation may be reused where it preserves the backup contract. Do not apply the normalization and collision strategies of the narrower import flows.

V1 is the first complete backup version and has no earlier complete-backup format to migrate at launch. Future versions should support older complete backups through explicit migrations where faithful conversion is feasible. A migrated file must satisfy the current validation contract and preserve the semantics of all supported records and relationships. A missing, malformed, or unsupported version, including a newer version the receiving build does not understand, must fail visibly with no collection changes. For a known but unsupported version, identify the version and advise using a compatible build.

Validate override records against the receiving build's canonical SRD IDs, supported locales, and verbal and somatic component eligibility. A missing translation for an otherwise supported locale and canonical spell remains distinct from an invalid override target. If any override is incompatible, reject the entire restore and identify every affected record's spell ID, locale, and incompatibility reason. Suggest opening the file with a compatible build. If the receiving catalog data needed for validation is temporarily unavailable, report that validation could not finish and allow retry. Never skip, alter, or store an incompatible override as inactive.

Treat backup files and displayed fields as untrusted data. Use bounded, safe validation and existing safe Markdown and text rendering rules. Export and restore are local operations. They require no upload, external assets, or service and work offline once the required bundled data is available.

### CB-4 — Review, confirmation, and atomic replacement

Provide a clearly named restore action distinct from deck-only and custom-spell import. Reading and validating a selected file, reviewing it, and canceling must leave the destination unchanged. Present the validated backup's active deck and counts of saved decks, custom spells, and SRD overrides. Warn explicitly that confirming replaces the entire current collection, including the committed working deck and local records absent from the file. Require a separate destructive confirmation for every restore, including an empty backup or destination. Only the specific reviewed file and destination state may be confirmed. Selecting another file or leaving review invalidates pending confirmation.

On confirmation, check review freshness and replace all four stores and advance the collection generation in the same IndexedDB transaction. The file defines the complete resulting collection. Existing records absent from it are removed and matching IDs receive only the backed-up values. Never merge, keep both, or use the old narrow import routines to perform sequential writes. Reads must observe either the old or the new committed collection.

Report success only after commit and refresh or reload the workspace from committed state, including resolved cards and available snapshots. If a post-commit refresh fails, report that restore committed and offer reload or refresh using existing recovery conventions. Do not label the committed replacement as rolled back or replay it. On failed file read, invalid or incompatible data, stale confirmation, quota exhaustion, unavailable storage, or an aborted write, report the appropriate failure and preserve the destination's previously committed data. If a transaction fails after any deletion or insertion, rollback must preserve the entire old collection and its concurrency metadata. Recovery from a failed transaction requires no backup of the destination.

### CB-5 — Concurrent tabs and stale actions

Support restore with other app tabs open. Bind the review to the committed destination state observed when the review is generated. Transactionally check, on commit, whether any in-scope collection mutation succeeded after that review. Use a persistent collection change token or equivalent that detects writes to every included store and other successful restores, even if values later return to their prior values. If the destination changed, do not write anything for this restore. Explain the conflict and require a newly generated review and explicit confirmation. Failed writes and actions that leave the persisted collection unchanged need not invalidate a review.

Maintain a persistent collection generation identifier or equivalent transactional guard. Advance the generation on every successful restore, even for an identical file, and do not import it from the backup. Every relevant mutation must verify the generation of the state on which it acts within its write transaction, before making any write. Generation checking complements existing record-level revision and collision checks. A token captured only when a delayed write finally executes cannot protect stale source state.

Cover all current collection-writing paths, including active-deck initialization and edits, saved snapshot operations, custom spell create/edit/copy/delete/undo, SRD overwrite and reset, both narrow import flows, and complete restore. Check queued operations, stale dialogs, and suspended tabs. Reject stale mutations, surface that the collection changed, and require fresh state and renewed user intent. Reopening or refreshing on a notification must not silently rebase a pre-restore draft or action. Notifications may speed refresh, but correctness must hold if they are unavailable or missed.

The persistence upgrade must preserve existing data and prevent an already-open app build that lacks the guard from writing to a restored collection. If an older client blocks a required storage upgrade, report the block and preserve the collection. Current, compatible tabs may remain open. The guard, change token, and read or refresh strategy are implementation choices within these guarantees.

## Scope boundaries

- Deck-only and custom-spell import/export retain their existing formats and user-facing semantics. Their writes participate in stale-action protection.
- The optional self-contained single-deck export and inactive override management are deferred. Data and settings introduced by separate feature requests are outside this specification.
- The scope is one browser origin's persisted collection, with portable JSON for manual transfer. Accounts, synchronization, scheduling, and hosted storage are outside the request.

## Acceptance criteria

| ID | Covers | Scenario and expected result |
| --- | --- | --- |
| AC-01 | CB-1, CB-2, CB-4 | Export a dirty, associated working deck with distinct baseline and saved entries, duplicate snapshot names, empty and populated snapshots, all fit modes, an unused custom spell, exact Unicode and Markdown content, optional fields, timestamps, and overrides in multiple locales. In one export activation obtain one file. Restore in an empty compatible browser context and reload. Compare supported values and record keys, active and baseline order, saved list order, revision tokens, dirty status, and reference resolution. No supported field or relationship changes. The receiving language preference stays the same, including when no preference is stored. |
| AC-02 | CB-1, CB-3 | Restore known missing custom and SRD references and an SRD reference with a missing translation. Keep original IDs, source, and fallback names, preserve placeholders, and verify that matching restored definitions resolve by ID and source. Round-trip a migrated association with an unverified baseline revision and verify existing recovery still applies. Exercise a stale baseline with a valid historical revision and verify a subsequent conflicting Save still reports the existing conflict. |
| AC-03 | CB-1, CB-4 | Restore over a populated destination containing distinct IDs and overlapping IDs. Verify no changes before confirmation or after cancel or dismissal. Confirm and verify that only the backed-up collection remains, the UI shows committed state, and it remains after reload. Export and restore an empty collection over a populated one and verify that confirmation is still required and the result is empty. |
| AC-04 | CB-2 | Race export against a transaction updating related records across stores. The output must represent either complete committed state. A read or serialization error produces no partial download. A supported collection above the old narrow import limits can be exported and validated for restore. |
| AC-05 | CB-3, CB-4 | Submit malformed JSON, a wrong type, a missing section, missing or unsupported versions, invalid nested data, duplicate identities, or invalid relationships. Each is rejected before confirmation, passes no partial records to storage, and leaves all destination data intact. Test explicit migrations with representative fixtures whenever older complete-backup versions become supported. |
| AC-06 | CB-3, CB-4 | Use a backup containing multiple incompatible overrides, including an unknown canonical ID, unsupported locale, and an ineligible component. Each affected spell ID, locale, and reason appears, and no record is restored. If validation data cannot load, show a retryable error and change nothing. |
| AC-07 | CB-4 | Inject an abort after replacement has begun and exercise quota or storage failure. Verify the entire prior collection and guard metadata remain committed and readable after recovery and reload, with failure feedback and no success report. If refresh fails after a verified commit, report the committed restore and allow a reload without repeating it. |
| AC-08 | CB-4, CB-5 | Generate a review in tab A. Modify each collection store in separate cases in tab B, including a record later changed back. Confirmation in A fails, preserves B's committed state, and requires a fresh review and a separate confirmation. Competing restores from the same observed state cannot both commit under the original confirmations. |
| AC-09 | CB-5 | Start stale edits, pending import plans, queued actions, and undo work before a restore. Attempt to finish them afterward from the same tab or a second tab, including when notifications are suppressed and record revisions or IDs match. All stale writes are rejected with no persisted effect and no automatic retry. New actions based on refreshed state can succeed. Verify mutation-layer coverage for each writing path and test suspended or delayed user actions in a multi-tab browser scenario. |
| AC-10 | CB-5 | Upgrade a database containing existing collection data and verify it survives. Exercise an older client during upgrade and confirm it cannot mutate the restored collection. If it blocks storage readiness, verify the attempted restore fails safely. |
| AC-11 | CB-2, CB-3, CB-4 | Complete export and restore in a warmed offline PWA using keyboard-accessible controls. Verify the destructive warning and outcome are accessible, the controls and messages are localized, and no collection data is sent over the network. Exercise both existing import/export workflows and confirm their formats and normal behavior remain intact. |

Use unit tests for format validation and fidelity, IndexedDB integration tests for rollback and mutation guards, and browser E2E tests for download, review, restore, offline behavior, and cross-tab effects. Existing [project verification guidance](../../DEVELOPMENT.md) applies to implementation.
